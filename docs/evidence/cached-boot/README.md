# Cached startup investigation, 2026-09-28

This is a **headless Chromium landscape** timing experiment, not an iPhone benchmark or a shipping gate. The viewport was 852×393, DPR 2, mobile touch UA, no audible mode, service worker enabled unless named otherwise. `measure.mts` loads one new context cold, then navigates the same tab twice from its filled cache, then turns the origin offline for two more navigations. It records each painted loader step, the first injected script, navigation timing, page errors, service worker control and the SHA-256 prefix of the served `index.html`. The build came from commit `351dfa90` plus the then-uncommitted course/map work. The full source state is not frozen; the HTML fingerprints below identify the two controlled outputs.

The two builds were **measurement only**. A temporary, deleted Vite config raised the bundle and inline-loader size gates, because the shared tree exceeded both during other work. It built into isolated `/tmp/rockhop-boot-before-dist` and `/tmp/rockhop-boot-after-dist`. The temporary config selected the prior `compileMaterials()` schedule for the first build and a proposed frame-budget schedule for the second. Other agents edited the shared tree during this period: the emitted map, retired, inbox and audio-offline chunks also differ, so the two outputs are **not a controlled A/B**. The normal gates were not relaxed in repository files, and neither build is shippable evidence. The renderer change was reverted after this exploratory comparison.

The proposed scheduling change moved measured post-script time by only about 0.1 s against larger run-to-run wall variation and a changing source tree; the shader step itself did not consistently improve. It is **reverted**, with no optimization claim. The biggest game-controlled phase remains shader preparation at roughly 1.1–1.3 s cached. The offline-pack step took about 0.43–0.51 s, and the first frame about 0.42–0.47 s. These are already inside a roughly 3.3–3.6 s post-script startup on this host.

The striking 5.6–7.9 s gap before the first script is a **headless Chromium navigation delay after the game ran**, not a measured JavaScript boot step. The cached HTML response ended in 2–5 ms, but `document_start` injection did not run until seconds later. Same-tab navigation and a fresh tab after closing the game both exhibited it. Disabling service workers entirely still gave a 6.50 s first-script delay; deleting the worker's background document revalidation gave 6.39 s. Most decisively, navigating the same tab from the game to the tiny static `offline.html` took 6.48 s: its response ended at 5 ms, and its first script ran at 6.47 s. That does not establish the cause inside Chromium, but it rules out the game's cached asset streaming and service-worker update as explanations for the gap in this harness. It also means the 9–11 s wall times above must not be presented as phone startup times.

All measured game boots had zero page errors, a controlling worker when enabled, and a rendered canvas and menu at loader exit. The investigation did not change loading UI or production code. Actual iPhone cached start, hero visibility, pixel stability and first Garage swap still need a device capture and timing report before claiming a ≤5 s device result.
