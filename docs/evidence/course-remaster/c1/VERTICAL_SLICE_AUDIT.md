## Ordered implementation brief

### 1. Make the first brake decision readable in real time

**Why first:** C1's [authored course](../../../../src/tracks/rockhop/coast.ts) asks the rider to settle a 22° pallet ramp after Marker 2. The fixed HUD approach cue spans x179.6–209.6, and the newer in-world BRAKE board sits at x195.5, **14.1 m before the ramp foot**. The [board's played report](../../c1-quality-next/README.md) says the ramp first enters the tight camera roughly one second before contact. The earlier [blind paused-step ride](../../c1-blind-play/played.mp4) needed four attempts/three bails; the cue conveyed “brake” but not the amount. Two later **briefed** CLI riders cleared in one attempt each ([session report](../../stranger-2026-09-29/README.md)). Held GO still clears 0/6 bike/seed trials, and the [fault evidence](../../c1-crash-feedback/README.md) shows a specific deck/causeway correction, one-second auto-respawn and next-tick manual restart. This proves a real skill gate and fast simulated retry, not that a new touch rider sees the ramp early enough.

**Build/check:** First run three uncoached landscape-phone rides and log when each rider notices the ramp/sign, what brake action they predict, x and cause of each fault, and time from Retry tap to controllable visible bike. If they see the board too late, reveal the ramp and landing earlier in the camera and move the physical warning upstream of the braking decision; keep contact geometry and the clean input unchanged in that pass. Show the ramp top and container landing together without hiding tire contact. Accept when all three can name the brake move before the lip, at least two clear, and a failed rider can explain the correction; preserve zero held-GO clears, both-bike exact finish hashes and next-tick control. Measure rendered restart latency on a physical phone rather than inferring it from simulation ticks.

### 3. Make the first reward and return path legible enough to invite a second run

**What works:** The user accepted the finish layout direction. The production [played result states](../../finish-remaster/state-audit/README.md) distinguish first clear, faster same-medal PB, Gold→Diamond upgrade and no-gain after reload; +220 then +80 Scrap pays once, and Retry/Replay/Map/Next reach their destinations. The full App flow carried a real Diamond, +300 Scrap and wallet to Garage. The selected clean Rookie run is only **0.25 s inside Diamond** ([medal audit](../../campaign-medal-audit/README.md)); two briefed CLI clears were slower. None of this measures whether a new rider reads the next goal or voluntarily chases it. The state audit found result tag/label text as small as 8–9 CSS px, later raised to 10; physical phone readability remains open.

**Build/check:** Keep the accepted report layout and earned Scrap logic. The [current-source integrated flow](current-map-first-win/README.md) now supplies an uninterrupted phone-size Menu→command-strip map→C1 ride→live report→Map→Garage→reopen recording; exact finish, saved medal, wallet and no duplicate Scrap pass. On a real landscape phone, ask each first-clear player to say their medal, next time/skill goal, Scrap-to-Pro progress and intended next button without coaching. If they cannot, enlarge/clarify the existing labels and make the next C1 improvement concrete (brake timing or a time delta) before adding reward mechanics. Require one of three players to **voluntarily** Retry or Replay for a better C1 result.

**Open before sign-off:** no uncoached real-time physical-phone C1 sample, no audible device mix, no sustained phone frame-time measurement, and no observed voluntary replay. The current command-strip first-win flow closes the source-integration check but does not certify art quality, human understanding or replay motivation.
