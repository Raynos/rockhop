The ten new MP4s use the production App in headless Chromium at **852 × 392, 20 fps**, renderer quality `high`, with no audio. Each browser clip's ending state hash matches Node at the exact ending input tick; all ten camera checks pass. The clips total **32.9 MB**, and no raw frames were kept. C3/A1/A3/D2/D3 show the final fault before that recording's eventual clear; D1 shows the first terrace fault; A2 has one fault. The three Snowline inputs were authored because the available CLI sessions used Pro, and the generated sequences were replayed in Node before browser capture. They hold the crash for 18 simulation ticks before manual restart so the fault is visible at 20 fps; each clip's camera record contains three crash frames. Their fast restart and forward progress prove control availability, not a human correction or clear.

Every report records the same full source-tree SHA-256 `e1c7f49b12d785cf2eec485a2a0ccc8c3130e8924b72fb638f547501ebd1d4ca`, the particular production build index hash, recording and MP4 hashes, selected fault and retry ticks, Node/browser end hashes, camera result, and full fault/restart event history. C1 and C2 are older sources and should not be treated as same-build comparisons.

**Measurement boundary.** A “fault → restart” number is simulation time from the fault event to a `riding` checkpoint-restart event. The subsequent number is simulation time to the first non-neutral recorded input. Snowline's 158.33 ms includes the deliberate 18-tick crash hold and the manual restart tick; it is not the minimum possible retry latency. These are deterministic game-rule measurements, not physical-phone touch-to-visible-control or frame-pacing latency. Changed input is a byte-level observation, not proof a new player understood the cause. A3 and D2 show restart and control, but the first active input did not change. Uncoached landscape-phone rides and measured visible restart latency remain open.
